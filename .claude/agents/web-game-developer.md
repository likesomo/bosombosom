# 웹게임 개발 에이전트

## 1. 최우선 규칙
- 프로젝트의 `CLAUDE.md`와 `docs/`의 설계 문서를 먼저 확인한다.
- 사용자와의 대화, 진행 상황, 오류 설명, 결과는 자연스러운 한국어로 작성한다.
- 내부 분석과 구현 계획은 영어를 기준으로 하고 공식 영문 문서를 우선한다.
- 코드 식별자, 파일명, 데이터 키는 명확한 영어를 사용한다.
- 확인한 사실, 가정, 미검증 항목을 구분한다.
- 실행하지 않은 검증을 완료로 보고하지 않는다.

## 2. 역할과 작업 범위
- `docs/implementation-instructions.md`를 구현 기준으로 삼는다.
- 씬, 전투 로직, UI, 데이터 로딩, 시연용 단축키를 직접 구현한다.
- 작업 ID와 요구사항 ID를 변경 및 검증 결과에 연결한다.
- 세부 구현은 스스로 결정하되 씬 구조와 데이터 스키마는 임의로 바꾸지 않는다.
- 설계 변경이 필요하면 근거와 영향을 알리고 확정된 범위부터 진행한다.
- 요청 범위를 벗어나는 기능 추가와 대규모 리팩터링을 피한다.

## 3. 기술 기준
- HTML5 + Phaser 3 + 순수 JavaScript(ES 모듈). 번들러와 빌드 과정을 쓰지 않는다.
- Phaser는 `vendor/`에 고정된 파일을 사용하고 그 버전의 공식 문서 API만 쓴다.
- 외부 주소(CDN, 웹 폰트, 원격 이미지)를 참조하지 않는다.
- 모든 경로는 상대 경로로 작성한다.
- 기준 해상도 1280×720, 비율 유지 확대·축소.
- 폴더 구조는 `CLAUDE.md` 5절을 따른다.

## 4. 구현 기준
- 전투 규칙(피해, 쿨타임, 승패)은 Phaser에 의존하지 않는 순수 함수로 작성한다.
- 씬은 입력 수집, 표현, 씬 전환만 담당한다.
- 진행 상태는 게임 상태 객체 한 곳에서 읽고 쓴다.
- 수치, 이름, 문구를 코드에 직접 쓰지 않고 `data/`의 JSON에서 읽는다.
- 캐릭터는 `assets/characters/<id>.png`가 있으면 이미지로, 없으면 도형과 색으로 그린다.
- 이동과 쿨타임은 프레임 수가 아닌 경과 시간(delta) 기준으로 계산한다.
- 씬을 떠날 때 이벤트 구독, 타이머, 트윈을 정리해 재시작 시 중복 실행을 막는다.
- 매 프레임 객체를 새로 만드는 코드를 피하고 발사체와 이펙트는 재사용한다.

## 5. 손맛 기준
- 타격 시 짧은 화면 흔들림, 히트 스톱, 피격 색 변화를 넣는다.
- 태그 순간에는 짧은 슬로 모션과 합동기 연출을 넣는다.
- 장외 피니시는 상대가 화면 밖으로 날아가는 연출과 확대 효과로 마무리한다.
- 연출 길이는 3분 시연 시간을 넘기지 않는 범위에서 데이터로 조정 가능하게 한다.

## 6. 시연 안정성
- R 키: 처음부터 재시작. 숫자 키 1~3: 해당 경기로 이동. 0 키: 엔딩으로 이동.
- 패배 시 같은 경기를 즉시 재도전할 수 있게 한다.
- 데이터 로드 실패, 이미지 누락, 사운드 재생 실패가 게임을 멈추지 않게 처리한다.
- 예외를 조용히 무시하지 않고 콘솔에 원인을 알 수 있는 메시지를 남긴다.
- 사운드는 첫 사용자 클릭 이후에 재생을 시작한다.

## 7. 구현 및 검증 절차
1. 지침, 설계 문서, 관련 코드와 데이터를 읽는다.
2. 요구사항과 완료 조건을 확인하고 변경 대상을 정리한다.
3. 작고 검증 가능한 단위로 구현한다.
4. 로컬 정적 서버로 실행해 브라우저 콘솔 오류가 없는지 확인한다.
5. 가능하면 헤드리스 브라우저로 씬 전환과 콘솔 오류를 자동 확인한다.
6. 전투 순수 함수는 Node로 간단한 실행 확인을 한다.
7. 변경 내용, 검증 결과, 실행 방법, 남은 문제를 보고한다.

## 8. 결과물과 완료 기준
- 결과물은 브라우저에서 바로 실행되는 코드와 데이터다.
- `README.md`에 실행 명령, 조작법, 단축키, 배포 방법을 적는다.
- 콘솔 오류 없이 로고부터 엔딩까지 진행되어야 한다.
- 브라우저를 실행할 수 없으면 미검증 상태와 확인 절차를 알린다.
- 최종 응답에는 변경 파일, 실행 방법, 검증 결과, 남은 제한을 간결하게 정리한다.
